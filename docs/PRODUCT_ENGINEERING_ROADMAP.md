# SimLoom AI 工程化路线图

SimLoom AI 的目标不是把四个商业软件重新做一遍，而是让工程师用一个稳定的入口完成：

```text
目标 → 计划 → 执行 → 结果 → 判定 → 可追溯交付
```

每一层都必须能在没有商业软件的机器上测试，并且在 Windows 工作站接入真实软件后保持
相同的工程对象、事务和验证边界。

## 当前最重要的产品原则

1. **默认可运行**：第一次启动就能创建项目、运行离线闭环、看到模型和指标。
2. **状态可解释**：用户始终知道当前是离线 surrogate、已连接、排练还是实际执行。
3. **失败可恢复**：每个写操作都有事务、日志、重试和 rollback；错误要告诉用户下一步。
4. **结果可审计**：输入、脚本、结果、规则、版本和哈希必须能一起导出。
5. **真实软件可替换**：CATIA、Ansys、Adams、VI-grade 只是 adapter，不能把厂商细节
   渗透到统一对象模型里。

## 建议的交付顺序

### P0：把离线原型变成可靠工作台

- 安装器、启动器和 Python 包元数据统一为 `simloom-ai`。
- 首页固定为一条五步路径：创建项目、输入目标、生成计划、运行、查看报告。
- `/api/doctor` 输出能力矩阵：离线、OpenCascade、LLM、Windows bridge 和每个软件的
  连接状态。
- 任务页面显示阶段日志、耗时、失败原因和“一键重试”。
- 统一错误 envelope 和 request id，用户界面显示可读消息，日志保留技术详情。
- 每次运行导出一个可分享的 `report.html` 或 `report.json`。

### P1：把工程结果做成可复用资产

- 项目模板保存参数、规则、工具链和输入文件版本。
- 版本时间线支持“从某次运行复制项目”和字段级 diff。
- 结果查看器支持几何、网格、标量云图和 CSV 曲线联动。
- 规则编辑器支持单位、范围、缺失值策略和工程结论说明。
- 大文件使用流式读取和分页，避免把整个结果文件加载到浏览器内存。

### P2：接入真实 Windows 软件

- 每个软件独立 worker，统一 `prepare → execute → collect → validate` 生命周期。
- 先做只读连接探针和模板校验，再开放写入和求解。
- 所有真实执行必须有显式 profile、超时、进程回收、日志采集和失败恢复。
- 用真实软件录制的最小 fixture 建立验收集：几何、网格、求解、结果回读各一例。
- 将 Windows worker 与本地工作台解耦，支持本机和远程 worker 两种部署。

### P3：团队化使用

- 项目权限、凭据隔离和审计导出。
- 共享 artifact registry 和项目锁。
- MCP schema 版本协商、分页、订阅和兼容性测试。
- GitHub Actions、Windows runner 和发布安装包自动验收。

## 每个版本的验收门槛

- 新用户在干净环境中 10 分钟内完成离线闭环。
- 失败任务可以从界面定位到阶段、日志和输入文件。
- 同一项目重复执行能得到可比较的版本记录。
- 没有商业软件时，所有核心测试仍然通过。
- 接入真实软件时，替换的是 adapter/worker，不能改变 Web、MCP 和验证接口。

## 下一轮建议直接实现的三件事

1. 能力矩阵和运行模式标识，让用户清楚“现在能做什么”。
2. 统一任务详情页和报告导出，让结果可以交付给同事或评审。
3. Windows worker contract 和四个只读连接探针，为真实软件接入建立稳定边界。
